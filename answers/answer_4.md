All the tests should still pass, i.e. the example with an empty string should trigger an error. However, code coverage is less than 100%, because it is not the line of code that checks for empty strings that is being triggered - it's the one that checks that all genotypes have the same ploidy. This makes sense: having one empty genotype among non-empty ones will be flagged as unequal ploidies before the function figures that there is an empty genotype, and so the "empty genotype" error is never triggered. To bring code coverage back up, you need to update the test to an edge case that will not be caught by the "unequal ploidy" check but still have an empty genotype. The only possible example is a vector consisting only of empty genotypes. And because we are already checking for unequal ploidies, we can save some computation by only looking at the first genotype when looking for empty ones: empty genotypes among non-empty ones would have triggered the unequal ploidy error, therefore the only remaining possibility for empty genotypes is that all genotypes are empty, and since when checking for empty genotype we already checked that all had the same ploidy, it follows that we can safely look just at the first genotype: if it is empty, all are. 

Bottom line: some tests may already be accounting for some scenarios we haven't thought of yet, which forces us to think extra hard about the opportunities for error we might have missed. We can also use that to optimize the way we check for errors in our code.
